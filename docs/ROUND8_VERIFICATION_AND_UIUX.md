# Round 8 — MSME feasibility workbook, end-to-end reconciliation, and UI/UX standardisation

> **Dokumen riwayat.** Verifikasi ronde 8 (2026-09-11) dengan workbook referensi lama. Importer itu digantikan templat Mankeu (DEC-012). Keadaan sekarang (Room schema 11): `README.md`, `docs/DOMAIN_MODEL.md`, `docs/V1_IMPLEMENTATION_SPEC.md`, `docs/diagrams/`, dan keputusan di `logs/DECISION_LOG.md`.

Three deliverables: a standardised MSME feasibility workbook that verifies the app end to end, a
UI/UX pass over the main screens, and the audit record below. Both items deferred at the first pass
— importing the workbook's own planning parameters, and deriving a plan cash schedule from a dated
RAB — are done and verified on a device. Everything claimed here has named
evidence; where something was deliberately not done, it says so under
[Known gaps](#6-known-gaps-and-what-was-deliberately-not-done).

## 1. The verification workbook

### 1.1 What it is

`simulasi_kelayakan_umkm_verifikasi.xlsx` is a complete feasibility study for a real-shaped MSME:
**Dapur Sambal Nusantara**, a bottled-sambal producer (Kuliner / makanan olahan) over one
three-month production cycle, February to April 2026.

It is generated by `scripts/generate_verification_workbook.py` — pure Python standard library, no
`openpyxl`, so it runs anywhere — which also writes the golden values to
`docs/evidence/verification-workbook/expected.json`.

| Attribute | Value |
| --- | --- |
| Filename | `simulasi_kelayakan_umkm_verifikasi.xlsx` |
| SHA-256 | `54e2a168de5cdee18db0c9564ee6a2361fde08d81849abdf3d0cd489c346deed` |
| Reproducible | Yes — every ZIP entry carries a fixed timestamp, so an unchanged generator writes a byte-identical file |

| Sheet | Role recognised by the importer | Contents |
| --- | --- | --- |
| `Petunjuk dan Parameter` | `PARAMETERS` | The eight assumptions the app cannot derive: capacity, unit price, own capital, loan, interest in bps, other financing cost, opening cash. Read into the projection book's Asumsi on import. |
| `RAB (Proyeksi)` | `BUDGET` | 45 plan lines in 11 sections, each dated to the month it is planned for. Lands in the **projection** book. |
| `Transaksi Harian (Realisasi)` | `DAILY` | 56 real transactions. Lands in the **realization** book. |
| `Laporan Laba Rugi` | `PROFIT_LOSS` | Formula-driven profit and loss over the ledger. |
| `Arus Kas dan Analisis Kelayakan` | `CASH_FLOW` | Monthly cash flow, working-capital gap, feasibility for both books, plan-versus-actual. |

### 1.2 Why the numbers can be trusted

Every derived figure on sheets 4 and 5 is written as **a live Excel formula carrying the cached
value that formula evaluates to**. Excel shows `=SUMIFS(...)`; the Mankeu importer reads the cached
`<v>`. Both are the same number by construction, because the cached value was computed in Python
using the same arithmetic the Kotlin domain uses — exact integer rupiah, `BigDecimal` with
`HALF_UP` for every ratio.

The generator refuses to write the file unless nine self-checks hold, among them:

- every amount is a positive integer rupiah;
- every `volume × harga satuan` equals its stated total;
- the cash balance equals the last cumulative cash figure, and operating + investing + financing
  equals the balance;
- every settlement points at a credit row that exists and never overpays it;
- every credit row names a counterparty;
- the profit-and-loss breakdown closes exactly onto Mankeu's single `Beban Operasional` figure;
- **no RAB line total appears on both the profit-and-loss sheet and the cash-flow sheet**, because
  three agreeing sources is precisely what `findDeterministicEnrichments` needs before it invents a
  transaction. Every fact in this workbook is stated once, in the ledger, so any such coincidence
  would be a false recovery and a double count.

The plan is profitable over the cycle and still Rp14.850.000 short in February, because the
equipment and the first month's stock land before the sales ramp. That trough *is* the working
capital, and it is what the Rp15 juta of own capital covers. An undated RAB could not have found
it — this is gap 2 of the previous round, now closed.

### 2.5 A naming note that matters

Mankeu's `reports_cost_per_output` is labelled **"HPP (Biaya per botol)"**, but the figure it shows
is `total biaya ÷ volume` — total cost per unit, *including* interest and financing charges. That is
not the accounting HPP (beban pokok penjualan), which for this case study is Rp114.680.000, or
Rp21.516 per bottle.

The workbook shows both, each under its own name, and states the difference on the sheet. The label
inside the app is the one to reconsider; the arithmetic behind it is correct and matches the
reference workbook contract.

## 3. Defects found and fixed

These were found by building the workbook and running it through the real code — not by reading it.

| # | Defect | Where | Consequence | Fix |
| --- | --- | --- | --- | --- |
| 1 | **A daily ledger could only produce cash income or cash expense.** `parseDailyLedger` had two outcomes per row. | `FinanceWorkbookImporter` | A capital injection, a loan disbursement, a credit sale, a debt repayment and an equipment purchase all arrived as ordinary revenue or ordinary expense. Profit, operating cash flow and financing cash flow were each wrong, and plausibly so. | Optional `Jenis` column, read through the new `TransactionKindLabels`, giving the daily ledger the full 13-kind event vocabulary. Companion columns `Pihak`, `Jatuh Tempo` and `No. Kewajiban` carry what obligations and settlements need. Rows that declare no `Jenis` behave exactly as before. |
| 2 | **A five-view workbook's RAB could be dropped into the wrong book.** `carriesBookMode` was true only for Mankeu's own export, so any other workbook showed a target-book picker — and `commitImport` applies that choice to *every* row. | `FinanceWorkbookImporter`, `MoreScreen` | Choosing "Realisasi", the obvious answer for a book of real transactions, sent the whole RAB into the realization book and left the plan empty. | A five-view workbook that carries a RAB does state which book each row belongs to; `carriesBookMode` is now `rabBudgets.isNotEmpty()`. With no RAB there is genuinely nothing to distinguish and the picker stays. |
| 3 | **RAB volumes stored as `"6000.0"`.** `parseRabBudget` read the volume cell through `display`, which stringifies a numeric cell. | `FinanceWorkbookImporter` | A plan line for 6.000 bottles read "6000.0 pcs" in the app. `parseGenericBudget` already formatted it correctly; this path did not. | Shared `quantityValue()` helper on both paths. |
| 4 | **Volume, unit and unit price were discarded on import.** `ImportCandidate` had no fields for them. | `ImportCandidate`, `commitImport` | A ledger row that says "400 kg @ Rp45.000" lost two thirds of itself, against the AGENTS.md rule that a user is never made to retype what the file already contains. | Three fields added and carried through to `MoneyEvent`, which already stored them. |
| 5 | **A plan book reported Rp0 across the board.** Every summary is derived from postings, and a projection book normally holds a costed RAB and no transactions. | `AppViewModel`, `HomeScreen`, `ReportsScreen` | Feasibility, break-even and B/C ratio all divide by a total cost. With no cost the plan side of Beranda and Laporan showed nothing at all, while a complete RAB sat one tab away. | New `BudgetPlanCalculator` turns a budget into the same `FinancialSummary` shape. It is a *declared* source class, used only when the book has no events, and the UI says so on the card — see `docs/DOMAIN_MODEL.md`, "A report must declare which source class it uses". |
| 6 | **"Kas setelah pembiayaan" was meaningless on the realization book.** The assumed-financing card was shown for both books. | `ReportsScreen` | On actuals the owner's capital and the loan are already recorded events, so adding the same assumed figures on top produced a figure that was neither the cash balance nor a plan. | The assumption card is now projection-only. The realization book gets a "Pembiayaan Terpakai" card built from actual movements. |
| 7 | **The shipped MSME template taught the wrong lesson.** Its "Setoran Modal Awal" row was imported as revenue. | `MsmeTemplateExporter` | Every owner who started from the app's own template counted their own Rp5.000.000 as sales. | The template now has a `Jenis` column, its capital row is `Modal Masuk`, and its equipment row is `Beli Alat Tunai` (an investing outflow, not an operating cost). `MsmeTemplateTest` asserts the corrected classification. |
| 8 | **Ampersands were back.** Round 4 had cleared them; `BusinessTemplate` and 30 strings reintroduced them. | `BusinessTemplate`, both `strings.xml` | Inconsistent with the house rule and with Indonesian usage. | Swept: 0 `&` remain in user-visible strings or default category names. Sector name "Kuliner / F&B" became "Kuliner dan Makanan Olahan". |

| 9 | **Every imported category was created as an operating expense.** `commitImport` passed a hard-coded `CategoryRole.EXPENSE` when a workbook named a category the business did not have. | `commitImport`, `parseRabBudget` | On a workbook whose names happen to match the business's own template this never showed. On any other one, a revenue target and a Rp13 juta equipment budget both became operating cost — so the plan's profit, its investing cash flow, and therefore its break-even and B/C ratio were all wrong, and wrong quietly. | `ImportBudgetCandidate` carries the role the workbook's own section heading implies. `parseRabBudget` now recognises ASSET sections as well as REVENUE and EXPENSE. |
| 10 | **The sector picker was never wired up.** `AddBusinessDialog` passed `BusinessSector.GENERAL_MSME` unconditionally. | `ManageScopeScreen` | Four sector templates existed, were tested, and were unreachable: an F&B owner started with "Stok dan Belanja Dagangan" instead of "Bahan Baku Makanan" and rebuilt the category list by hand. Lint had been reporting all four sector strings as unused resources — the symptom was visible, nobody read it as one. Found by creating a business on the emulator and counting the categories. | An `ChoiceMenu` for the sector in the create-business sheet, defaulting to UMKM Umum. |
| 11 | **"Total RAB" summed revenue targets into planned cost.** | `AppViewModel` | A plan with a Rp168 juta sales target reported Rp309 juta of budget, so the Realisasi vs Target comparison row measured nothing. | Revenue-role lines are excluded from the budget cost total. |
| 12 | **The speed dial covered the last card.** A `LazyColumn` scrolls under a `Scaffold` FAB. | `HomeScreen`, `EntryScreen` | The bottom item on Beranda and Catatan was permanently half-hidden. Found by looking at the running app. | 96dp bottom content padding on both lists. |

Defects 1, 3, 4 and 7 all belong to the same root cause: **the importer treated a daily ledger as a
two-column cash book**, which is true of the golden padi workbook and of nothing else an MSME keeps.
Defects 9 and 10 share another: **a default that was never revisited** — one in the commit path, one
in a dialog — each quietly correct on the one case that was tested and wrong everywhere else.

## 6. Known gaps and what was deliberately not done

1. **Realisasi assumptions are still entered by hand.** The workbook's parameters describe the
   *plan*, so they are written to the projection book only. The realization book's output volume is
   a fact of its own ledger, not an assumption, and deriving it automatically is a separate change.
2. **No Excel round trip by eye.** The workbook's structure is verified by the app's own OOXML
   reader, which is what the import path uses, and its formulas are plain `SUMIFS`, `ROUND`, `MIN`,
   `MAX` and cell arithmetic with `fullCalcOnLoad` set. A human should still open it once in Excel
   or LibreOffice.
3. **Seven pre-existing tests still skip.** They need the sibling
   `arina-finance-workbook-fixtures` repository, which is not on this machine. The new
   `VerificationWorkbookTest` does **not** skip: it fails hard if the workbook is missing.
4. **The plan schedule ignores financing timing.** `BudgetPlanCalculator.schedule` reports
   financing as zero for every month, because a RAB carries costs and targets, not a disbursement
   date. The financing assumptions are a cycle total. Dating them would let the plan show when the
   loan actually has to arrive, not only how much of it is needed.
5. **Machine-scope PATH still carries the quoted segment.** See the environment note in section 7 —
   fixing it needs an elevated shell, so it was left to the owner. The build no longer depends on it.

(`"E:\Android\Sdk\tools;E:\Android\Sdk\platform-tools"`). Those quotes break argument quoting for
the forked Gradle test worker, which then fails with

before invoking Gradle is enough. This is a machine setting, not a project defect, but it will hit
anyone else on this box.
