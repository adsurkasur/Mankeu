# Decision Log (Architecture Decision Records)

### [DEC-029] Fase 2: Sale Notes, Receivables, Supplier Credit, Consignment (Schema 14)
- **Date**: 2026-10-29
- **Status**: Accepted; schema, journals, migration and backup upgrade (Task 2) and the repository layer (Task 3) implemented on branch `fase2-nota-piutang`. Profit and screens follow in Tasks 4 to 8.
- **Context**: Owner decisions F2-1..F2-7 (redesign spec): notes with several products, unpaid and partly paid notes, consignment, credit from suppliers, profit when goods are sold. Schema 13 records a product sale only as a cash income event.
- **Decision** (planner rulings; each: decision, reason, cost if wrong):
  1. **One cash account.** No cash/transfer split or bank accounts; phase 2 is about bills, not wallets. Cost if wrong: an account column on events later.
  2. **A note payment is a `CASH_INCOME` event with `saleId`.** Journal Kas / Piutang, not revenue; the note recognises the revenue. A paid note = note + one payment on the same date, created automatically. Cost if wrong: a new event type if payments must be split off.
  3. **A credit purchase is the new event type `CREDIT_PURCHASE`** (no cash; Beban / Utang) with `contactId` and `dueDateEpochDay`. It is paid by a `CASH_EXPENSE` with `settlesEventId`, journal Utang / Kas. A credit purchase may link a material and set its price (#20) like a cash purchase. Cost if wrong: one more event type mapped in reports.
  4. **Profit comes from `ProfitCalculator` over the data, not from postings.** Revenue = note totals after discount (note date) + non-product income without a note; HPP = sum of line HPP snapshots; cost = spending (cash or credit, purchase date) whose effective cost nature is not `VARIABLE`; variable spending shows as "Belanja produksi (lewat HPP)" plus a variance line (F2-1); depreciation as in `PlanAssembly.actualMonth`. Note and supplier payments are neither revenue nor cost. Cost if wrong: one calculator replaced in F4.
  5. **A note discount is shared over its lines by value** (half up, remainder to the last line), only for per-product reports. Cost if wrong: per-product profit moves by Rp1.
  6. **Note status is derived:** paid (paid >= total), partial, unpaid; overdue = unpaid/partial and due date before today. Consignment is not a status but its own document that produces a note when sold (F2-6). Cost if wrong: none, always recomputed.
  7. **A note stores unit, content, price and HPP per line (snapshot).** Editing a product does not change old notes; editing a note recomputes its line HPP at edit time, with a notice. Cost if wrong: an edited old note takes today's HPP.
  8. **Product stock:** a note takes quantity × content; consignment takes stock "in the warehouse" and adds "consigned" per store; a sell-through note (with `consignmentId`) does **not** take stock again; a return (`CONSIGN_RETURN` movement) puts it back. Shown stock = warehouse; "consigned N" shown apart. Cost if wrong: stock figures need review.
  9. **Contacts per business** (not per unit), synced by natural key (`businessId`, `normalizedName`); archived, not deleted, once used. Cost if wrong: a unit column later.
  10. **Old data (F2-4).** Every Realisasi `CASH_INCOME` naming a product becomes a paid one-line note (`hppEstimated = 1`) and the event becomes its payment (`saleId` set, same id, journal rebuilt as Kas / Piutang). Line HPP is the recipe cost at migration time. Note id `<eventId>-s`, line `<eventId>-l`, timestamps from the event, so two phones migrating on their own produce the same rows. Old purchases stay cash purchases. Cost if wrong: old HPP is an estimate, and it is flagged.
  11. **The money-in form no longer offers products;** product sales always go through a note. Cost if wrong: users used to it must move to the Nota button.
  12. **Navigation until F3:** the record FAB gets "Nota penjualan"; Catatan lists notes above transactions with a "Belum lunas" filter; Beranda gets a "Tagihan" card; Kontak opens from the Data menu. Cost if wrong: F3 moves them.
- **Implementation choices (Task 2):**
  - `CREDIT_PURCHASE` always debits `OPERATING_EXPENSE` (the brief allowed limiting it to expense): an asset bought on credit is not offered; Task 3 must refuse a non-EXPENSE category. Its stored `cashFlowRole` is `OPERATING`, which never reaches a cash figure because it posts no cash; `MonthlyCashFlow` counts it as 0.
  - **`product_movements.consignmentId`** (nullable, no foreign key) was added beyond the brief: a `CONSIGN_RETURN` must say which consignment (so which store) the goods came back from, or per-store balances cannot drop. Deleting a consignment must delete its returns explicitly (Task 3).
  - Migrated line: unit = event unit, else the main sale unit, else the base unit; content from `ProductRecord.contentOf` (same rule as Fase 1 stock); quantity = event quantity, else 1; unit price = event unit price, else amount ÷ quantity half up; total = event amount; HPP = `ProductCosting.hpp(batch cost, batch yield, content × quantity)` with material prices derived exactly as `FinanceRepository` does (latest linked purchase with a price above zero by date, time, rowid; else the item's price; the business's own items only). A sale whose product no longer exists gets content 1 and HPP 0 (still flagged estimated).
  - The conversion runs with change capture off (`SyncSchema.quietly`); `SyncSchema.createTriggers` then covers the five new tables. A schema-13 phone refuses schema-14 change sets (existing `schemaVersion <= own` rule).
  - `updateEvent` (old Ubah form) keeps `saleId`, `contactId`, `dueDateEpochDay` and `settlesEventId` of the edited event, so a note payment edited there stays Kas / Piutang.
  - A migrated note keeps the sale event's `importBatchId`, and `undoImportBatch` deletes the notes of the batch (lines cascade), so undoing an import made before schema 14 leaves no note behind (DEC-012; review I-1).
  - When the event's unit name no longer exists (renamed or removed since), the line takes the main unit's name, the unit whose content it counted (Fase 1 `contentOf` rule), instead of a name that contradicts its content (review M2). Without the product, the event's unit name stays.
  - **Sync refuses change sets older than schema 14** (`SyncEngine.MIN_SYNC_SCHEMA`, review I-2): a schema-13 phone records product sales without notes and would overwrite migrated Kas / Piutang journals with Kas / Pendapatan, so the phones' books would differ for good. The error reads "Perbarui aplikasi di semua HP, lalu sinkronkan lagi." Release note: **sync every phone, then update every phone before syncing again.** Such a change set is skipped, not a wall (controller ruling, fix round 2): `SyncCoordinator` moves the cursor past it, counts it in `Report.skippedOutdated`, and the owner gets one notice and message ("Perubahan dari HP yang belum diperbarui dilewati; data lengkapnya akan datang setelah HP itu diperbarui."). Change sets newer than the phone's schema still block. `Migration13To14` sets `requires_full_snapshot` (harmless with sync off: switching on sets it too), so each upgraded phone republishes everything in converted form and recovers what was skipped; deletions inside skipped change sets are not replayed.
  - Backups are captured `ORDER BY rowid`, so the 13 → 14 upgrade breaks purchase-date ties exactly as the migration does (review M5).
  - Sync references: `contactId` -> contacts and `saleId` -> sales are rewritten through aliases; `DATA_TABLES` puts contacts after businesses and consignments, consignment lines, sales, sale lines after product movements, before `financial_events`.

### [DEC-028] Fase 1 Product Model: Sale Units, Per-Batch Recipe, Product Stock (Schema 13)
- **Date**: 2026-10-29
- **Status**: Implemented (Tasks 1 to 7 on branch `fase1-produk-hpp`, emulator walk in `docs/audit/2026-10-29_UJI_FASE1.md`); the nine rulings still await owner review.
- **Context**: Redesign spec #5 (base unit plus sale units), #6 (HPP from a per-batch recipe), #9 (automatic product stock with Produksi) and #20 (material price from the last purchase, warning when HPP changes). Schema 12 stores one unit at one price and recipe components "Rp X covers N units", which cannot express any of these.
- **Decision** (each: decision, reason, cost if wrong):
  1. **`stock_items` is reused as the material list.** It already holds name, unit and purchase price, so no new table. Cost if wrong: non-material trade goods share the list (labelled "Bahan & barang").
  2. **Material price is derived, not stored.** Price = `unitPriceRupiah` of the latest expense (date, then time recorded) linked to the material through `financial_events.stockItemId`; without one, the price entered when the material was created. Deleting a purchase restores the previous price by itself. Cost if wrong: one extra query when reading materials. (Task 2 still uses `basePriceRupiah`; Task 3 derives it.)
  3. **Buying a material does not add material stock.** Material stock stays manual (Masuk/Keluar/Opname), because #9 says production does not consume materials; if purchases added and production never subtracted, the number would only grow. Cost if wrong: owners who expect automatic material stock must record Masuk themselves.
  4. **Product stock is derived from sales.** No "out" row is written on a sale. Stock = production, counts and sales (product + quantity × unit content) in date order, so editing or deleting a sale is right at once. Sales from before the update count too, so stock can be negative until the owner records production or a count; the screen says so. Cost if wrong: testers see negative stock after the update.
  5. **The per-sale HPP snapshot (#6) moves to Fase 2.** The sale record changes completely there (multi-product notes, #17), and profit at sale (#3) is computed there too. Cost if wrong: none, Fase 1 reports do not use HPP.
  6. **The old product shape (schema 12 / template v4) is converted by one adapter, `LegacyProductShape`.** Each product becomes a batch of 1 base unit; its old unit becomes the first sale unit (content 1, id `<product>-u0`); each component "Rp X for N units" becomes a free line of `round(X ÷ N)`, half up. Rounding is at most Rp0,5 per component per unit. Ids come from the data, so two phones migrating on their own produce the same rows. Cost if wrong: an old product's HPP may move by Rp1.
  7. **Sync between versions.** The existing rule is `incoming schemaVersion <= own`: a schema-12 phone refuses change sets from a schema-13 phone, and a schema-13 phone accepts a schema-12 phone's changes. Product changes a schema-12 phone sends to a schema-13 phone lose their sale units and recipe (the old table is ignored; a product created there arrives without a sale unit and stays out of the plan until edited). Release note: "update every phone". Cost if wrong: products edited on an old phone during the transition must be filled in again. *(The plan wrote the first sentence the other way round, "schema 13 refuses schema 12"; the code does the reverse, recorded here as it behaves.)*
  8. **The first sale unit is the main unit.** The business plan (target per month, BEP) and the sale form's default use it until Fase 3 reworks the plan; the plan prices a product by that unit with its HPP as the one variable cost. Cost if wrong: unit order has to be rearranged in the editor.
  9. **The Excel template goes to v5 for the product sheets only** (plus Satuan, Bahan and Harga Satuan columns on Transaksi), so DEC-012 "an export re-imports without loss" holds in every release. v4 files are rejected (their Produk header does not match) with a clear list of problems. The full template and friendly rejection stay in Fase 5. Cost if wrong: the product sheets are rewritten again in F5.
     *Amended 2026-10-29 (final review I-1, controller ruling):* v5 also has a required sheet **Produksi & Stok** (Tanggal, Produk, Jenis = "Produksi" / "Hitung stok", Jumlah (satuan dasar), Batch, Catatan) holding a product's full production and count history, not a single stock level. Rows are imported only for products in the same file's Produk sheet that the import adds; a row naming a product not in that sheet is rejected, and the rows of a product skipped because the unit already has one of that name are skipped with it (the notice says so). So undo removes them with the product (FK cascade) and needs no `importBatchId` on `product_movements`. The file has no time of day, so one order rule applies: on one date, Produksi & Stok rows count after that day's sales, in file order. A count taken before same-day sales of that product therefore re-imports as if taken after them (the end-of-day count is the common case). Cost if wrong: such a count must be moved to the previous day in the file, or a time column added in F5.

### [DEC-017] Seasonal Products, Per-Unit Stock and Reversible Plan Period (Schema 10)
- **Date**: 2026-10-21
- **Status**: Accepted (agent; the owner delegated technical decisions and asked for real-flow tests). Implemented and verified on the emulator (`docs/audit/2026-10-21_UJI_SCHEMA10.md`).
- **Context**: Open items 1–5 of the cross-business test (`docs/audit/2026-10-21_UJI_ALUR_LINTAS_USAHA.md`). A chilli harvested in month 3 was planned as selling from month 1, so capital need was understated; reversing an import left the plan period it had filled in; stock belonged to the business, so one branch's stock appeared and was exported in every unit; the selection was forgotten on restart; import counts included skipped rows.
- **Decision**:
  1. `products.sellFromMonth` (1 = first plan month). A product sells in s = n − start + 1 of the n plan months. The cash schedule uses the real months, so capital need sees the waiting months. "Per month" revenue, cost, profit and BEP rupiah are averages over the period (weight target × s), so profit/month × n = period profit. Unit BEP per product is per **selling** month: FC × target × n ÷ Σ(target × s × CM). With every product selling from month 1 the formulas are exactly the previous ones. A product starting after the period sells nothing and has no BEP. Screens, PDF and Excel say so when a plan is seasonal.
  2. Template v4 adds the optional column "Mulai Dijual (bulan ke-)" on Produk. Optional columns (`MankeuTemplate.OPTIONAL`) may be absent (v3 files still import) but, when present, must carry the exact header. This is the only relaxation of DEC-012's exact-header rule.
  3. An import batch records the period it filled in (`appliedStart/EndEpochDay`); reversal clears the unit's period only if it is still exactly that one.
  4. `stock_items.projectId`: a unit sees its own items plus shared ones (NULL). New items default to the selected unit; "Semua unit" makes them shared. Names are unique within what one unit can see. Import adds stock to the selected unit (DEC-012 bulk entry). Existing stock stays shared on upgrade. A unit holding its own stock is archived, never deleted, so the stock cannot be orphaned. Partly supersedes DEC-010 ("stock belongs to the business").

### [DEC-016] Break-Even Base, Capital Need and Plan-vs-Actual Basis
- **Date**: 2026-10-21
- **Status**: Accepted (implementation, found by cross-business simulations).
- **Context**: Simulations of a farm, laundry, shop and tractor rental showed three definitional gaps: variable costs outside recipes were in profit but not in break-even (profit was negative at "BEP"); capital need was netted against planned capital, so planning capital hid the need; and Realisasi vs Target compared a 12-month plan total with one month of actuals.
- **Decision**: (1) Break-even base = fixed cost + variable costs not in any recipe − other income; profit is exactly zero there. (2) Capital need = deepest cumulative deficit of operations and investment before capital; planned capital and the remaining shortfall are shown next to it. (3) Plan-vs-actual compares averages per month (plan months vs recorded actual months), on a cash basis; the RAB total row is removed. (4) Mix BEP uses one exact division, FC × target × P ÷ Σ(target × CM). (5) The plan period travels in the template (`Petunjuk` row "Periode rencana") and fills a unit that has none.
- **Alternatives considered**: allocating non-recipe variable costs to units (rejected: needs an allocation key the owner never gave); comparing totals over the overlapping months only (rejected: plans are not split by calendar month yet).
- **Affected components**: `domain/BusinessPlan.kt`, `PlanCards.kt`, `ReportsScreen.kt`, exporters, importer, `FinanceRepository.commitImport`, template v3 guide sheet.

### [DEC-013] Multi-Device Sync Framework over Google Drive (End-to-End Encrypted)
- **Date**: 2026-10-20
- **Status**: Accepted (owner); framework implemented and tested, not wired to UI or scheduler.
- **Context**: The owner asked for sync infrastructure that is "framework-ready" without shipping the feature. The earlier design (`CLOUD_SYNC_AND_AUTH.md`) deliberately limited Drive to snapshot backups. The owner chose multi-device sync, with data on Drive encrypted by the user's passphrase.
- **Decision**:
  1. Change capture by SQLite triggers on every data table into `sync_outbox`, silenced by a `sync_meta.applying_remote` flag while applying remote changes or restoring. Created in `MIGRATION_7_8` and in a Room `onCreate` callback.

### [DEC-003] Realignment of CVP (Break-Even Point) and Ratio Metrics
- **Date**: 2026-10-18
- **Status**: Accepted
